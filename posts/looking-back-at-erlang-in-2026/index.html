2026 回看 Erlang：当现代基础设施仍在重写四十年前的答案

1986 年诞生于爱立信实验室的 Erlang，曾长期被主流工业界视作语法怪异的“电信古董”。然而站在它四十周年的节点回望，从云原生基础设施到有状态分布式运行时，再到如今无处不在的 AI Agent 编排框架，主流技术栈兜了一个巨大的圈子，正在用十倍的复杂度把 BEAM 虚拟机三十年前就已跑通的原语重新发明一遍。

1986 年，Joe Armstrong、Robert Virding 和 Mike Williams 在瑞典爱立信计算机科学实验室（CSLab）开始鼓捣一门后来被称为 Erlang 的语言时，他们面对的根本不是“如何把单颗 CPU 的算力压榨到极致”，而是一个极其苛刻的工程问题：

如何用必会写出 Bug 的软件，跑在必会断电或损坏的硬件上，构建出一台永不停机的电话交换机？

十二年后，爱立信推出了包含近两百万行 Erlang 代码的 AXD301 ATM 交换机，在工业界跑出了著名的 99.9999999%（9 个 9） 可用性——折算下来，系统每年的计划内与计划外总停机时间不超过 31.5 毫秒，而且支持在不中断通话的前提下在线热升级代码。

然而在此后的二十多年里，主流软件工程走上了一条截然不同的道路：我们先是沉迷于面向对象与共享内存多线程，试图用越来越复杂的锁和并发容器驯服数据竞争；接着又在云计算浪潮中转向了“无状态服务（Stateless Services）+ 外置数据库 + 消息队列 + 容器编排”的架构范式——既然进程管不好状态、也扛不住崩溃，那就把状态全部剥离到进程外部，再靠 Kubernetes 替我们重启容器。

直到 2026 年——Erlang 诞生整整四十周年的今天，当我们重新审视现代后端与分布式基础设施的演进方向时，会发现一个令人忍俊不禁的事实：无论是 Go 与 Rust 围绕异步运行时的修修补补，还是以 Temporal、Restate 为代表的持久化执行（Durable Execution）引擎，乃至当下最火热的 Multi-Agent 编排系统，所有人都在有意无意地重新拼凑一台“外置版的 BEAM 虚拟机”。

1. 并发的假象：为什么“协程”不等于“进程”

过去十年，Go 的 Goroutine、Rust 的 tokio 以及 Java 21 引入的虚拟线程（Virtual Threads）彻底普及了“百万级轻量并发”。于是很多人产生了一种直觉：既然主流语言都已经拥有了用户态 M:N 调度器，Erlang 引以为傲的轻量级进程（Process）是不是早就失去护城河了？

如果你只拿并发原语来跑 wrk 基准测试、比拼空转 HTTP 吞吐量，确实很容易得出这个结论。但在真实的生产系统里，主流语言的协程解决的是 I/O 复用效率，而 Erlang 的进程解决的是 故障隔离与确定性尾延迟（Tail Latency）。这两者在虚拟机底层有着本质的分野。

1.1 共享堆 vs. 私有堆（Per-Process Heap）

无论是 Go 的 Goroutine 还是 Java 的虚拟线程，本质上仍然是共享内存模型下的有栈/无栈协程。成千上万个协程依然共享同一个全局堆（Shared Heap）。共享堆会带来两个无法回避的工程代价：

  1. 崩溃半径是整个操作系统进程：只要有一个 Goroutine 触发了未捕获的 panic、空指针解引用，或者两个协程同时写入同一个 map（触发运行时的 fatal error: concurrent map writes），整个 OS 进程就会瞬间陪葬，正在同一进程内处理的另外一万个长连接也会同时断开；
  2. 垃圾回收（GC）是全局耦合的：即便现代分代/并发 GC 已经把 Stop-The-World（STW）压到了亚毫秒级，当某些协程突然分配大量内存时，全局写屏障（Write Barrier）、后台标记线程的 CPU 抢占以及分配器锁竞争，依然会让同一节点上毫不相干的业务协程出现毛刺。

而在 Erlang 的 BEAM 虚拟机中，一个 Process 根本不是“线程”，而是一个完全不共享内存的独立虚拟计算机：

  • 极致的创建成本：在 64 位 BEAM 上，创建一个新进程的初始内存开销只有 309 个机器字（约 2.4 KB），耗时在微秒级；
  • 私有堆与栈（Private Heap & Stack）：每个 Erlang 进程拥有自己独立的进程控制块（PCB）、私有邮箱（Mailbox）、私有栈与私有堆。栈和堆甚至位于同一块连续内存的南北两端，相向生长，因此栈扩容连内存拷贝都不需要；
  • 消息传递深拷贝（除大二进制块外）：进程 A 向进程 B 发送消息 PidB ! Msg 时，数据会直接从 A 的私有堆复制到 B 的私有堆（唯一例外是大于 64 字节的不可变二进制数据 Refc Binary，存放在全局堆中通过原子引用计数共享零拷贝视图）。

这种看似“浪费了一点内存拷贝”的设计，换来了两个极其恐怖的系统特性：

  1. 进程死则内存灭，许多时候甚至不需要 GC：在 BEAM 中，大量进程是短生命周期的（例如处理一次请求或一次工具调用后即退出）。当进程终止时，它独占的那块私有堆内存直接被分配器整体回收，连垃圾回收器都无需启动；
  2. 纯局部 GC（Per-Process GC）：即便长生命周期进程需要触发 GC，也只会在它自己那几 KB 到几十 KB 的私有堆上进行分代回收。进程 A 在做 Full GC 时，同一颗 CPU 核心上的进程 B、C、D 完全零感知。

1.2 协作式挂起 vs. 基于 Reduction 的预算抢占

另一个常被忽视的差异在于调度器的抢占粒度。

Rust 的 async/await、Node.js 乃至早期的 Go 调度器，本质上都依赖 I/O 边界或函数序言（Function Prologue）处的协作式让出（Cooperative Yielding）。如果某个任务落入了一段密集的 CPU 循环、复杂的 JSON 反序列化或病态的正则匹配，同线程运行队列里的其他任务就会遭遇严重的队头阻塞（Head-of-Line Blocking），导致系统 P99 延迟陡增。

BEAM 从诞生第一天起就是为软实时（Soft Real-Time）电信交换设计的，它采用的是基于归约计数（Reduction-based）的严格抢占式调度：

  • 在 BEAM 中，每一次函数调用（Function Call）或内置函数（BIF）执行，都被计量为 1 次归约（Reduction）；
  • 每个进程每次被调度器选中执行时，只会被授予 4000 个 Reductions 的预算；
  • 一旦 4000 次归约耗尽（通常不到 1 毫秒），或者进程主动阻塞在 receive / I/O 上，BEAM 调度器会无条件强行挂起该进程，将其放回运行队列尾部，切换下一个进程。

这种架构带来的真实体感是：当你把一台跑着 Go 或 Java 服务的机器 CPU 压到 95% 时，接口超时和毛刺往往呈指数级恶化；而当你把一台 BEAM 节点的 CPU 压到 99% 时，所有请求只是均匀地慢了一点点，SSH 远程连进 Erlang Shell 依然丝滑跟手。

2. “Let It Crash” 不是摆烂，而是状态重置的数学最优解

几乎所有听说过 Erlang 的人都听过那句著名的格言：“任其崩溃（Let It Crash）”。但这句话也是工业界误解最深的一句话——在习惯了防御式编程的工程师听来，“让它崩”简直等同于不负责任。

要理解为什么 Erlang 敢“让它崩”，首先要回答一个更本质的问题：为什么我们的程序会崩溃，以及为什么主流语言不敢崩？

2.1 海森堡 Bug 与共享内存的“脏状态污染”

1985 年，图灵奖得主 Jim Gray 在其奠基性论文 《Why Do Computers Stop and What Can Be Done About It?》 中对串联系统故障做过一次著名的统计剖析。他将软件故障分为两类：

  • 波尔 Bug（Bohrbug）：像波尔原子模型一样确定无疑、输入固定就必然复现的逻辑错误。这类 Bug 绝大部分在单元测试、集成测试和灰度阶段就会被消灭；
  • 海森堡 Bug（Heisenbug）：只在特定的并发时序、网络抖动、内存碎片或罕见状态交织下才会触发的瞬态故障（Transient Fault）。当你试图挂载调试器或加日志复现它时，因为时序改变，它又神秘消失了。

Jim Gray 指出，在已经通过测试上线的大型生产系统中，超过 99% 的致命故障都是 Heisenbug。对付 Heisenbug 最有效的手段，不是写上万行 if (err != nil) 去猜测所有不可能的异常分支，而是立刻丢弃已经被污染的局部瞬态状态，将出问题的单元重置回已知良好的初始状态（Known-Good State）。

然而，在 C++、Java 或 Go 这类共享内存语言中，你根本无法安全地只丢弃局部状态。想象一个线程持有一把互斥锁，正在修改一棵全局内存树的左子树，突然因为某个边界条件抛出了异常：

  • 如果你不用 try/catch 兜住，整个操作系统进程直接挂掉；
  • 如果你用 try/catch 或 recover() 强行把异常吞掉了，情况往往更糟——因为那棵内存树才改了一半，不变式（Invariant）已经被破坏，锁甚至可能没正确释放，整个进程实质上已经进入了静默脑死亡（Corrupted State）。

2.2 隔离 + 死亡信号 + 监督树（Supervision Tree）

Erlang 之所以能把“Let It Crash”变成工程现实，是因为它在语言运行时层面提供了三根支柱：

  1. 完全隔离的失败边界：因为进程之间不共享任何可变内存，进程 A 在计算中途崩溃，它的私有堆瞬间销毁，绝对不可能在邻居进程 B 的内存里留下一半改坏的指针；
  2. 内核原语级的双向链接（Link）与单向监控（Monitor）：通过 link(Pid) 或 monitor(process, Pid)，进程之间可以建立跨节点透明的生死契约。一旦某个进程因异常（非 normal）退出，BEAM 虚拟机底层保证向链接它的监管者投递一条 {'EXIT', FromPid, Reason} 消息；
  3. 分层监督树（OTP Supervision Tree）：在 Erlang/OTP 中，进程被组织成一棵严格的树。叶子节点（Worker）只管心无旁骛地写正常业务逻辑（Happy Path），连防御性的 try/catch 都不用写；树干节点（Supervisor）不写任何业务逻辑，只负责监控子节点并按策略重启。

看一段典型的 Erlang/OTP 代码就能体会这种极致的简洁。假设我们编写一个负责维护某个设备会话状态的 gen_server 工作进程：

而在它的上游，一个声明式的 supervisor 用短短十几行配置就定义了完整的故障自愈拓扑：

erlang
1-module(session_sup).
2-behaviour(supervisor).
3
4-export([start_link/0, init/1]).
5
6start_link() ->
7 supervisor:start_link({local, ?MODULE}, ?MODULE, []).
8

14 SupFlags = #{
15 strategy => one_for_one,
16 intensity => 5,
17 period => 10
18 },

20 #{
21 id => device_worker,
22 start => {device_session, start_link, ["dev-001"]},

24 shutdown => 5000,
25 type => worker
26 }
27 ],
28 {ok, {SupFlags, ChildSpecs}}.

请注意 intensity 与 period 这两个参数背后的工程智慧：它就像家庭配电箱里的分级空气开关。插座短路了，先跳支路空开（重启单个 Worker）；如果支路空开合闸 5 次连跳 5 次，说明根本不是瞬态抖动，而是整条回路出了结构性故障，此时支路放弃挣扎，直接触发上一级总闸跳闸（重置整棵子树及其共享连接池）。

3. 当云原生用十个组件重造一个 BEAM 节点

站在 2026 年回望过去十年的云原生（Cloud-Native）演进史，最令人感慨的一幕莫过于：现代后端架构花了整整十年时间，用 Linux 容器、YAML 配置和网络代理，把单个 BEAM/OTP 运行时原本就自带的能力，在操作系统层面笨重地重造了一遍。

在主流无状态微服务架构中，由于语言运行时本身不具备细粒度隔离、位置透明通信、进程监督和内置状态存储能力，我们不得不向外堆叠一长串基础设施中间件：

The Cloud-Native Tax
每当你把原本可以在进程内通过微秒级消息传递完成的交互，拆成跨容器、跨进程边界的调用时，你都在隐式缴纳一笔高昂的“基础设施税”：Protobuf/JSON 序列化与反序列化、内核 TCP/IP 协议栈穿透、Sidecar 代理转发、连接池保活、分布式超时重试，以及最终一致性的分布式状态对账。

分布式事务存储 外置分布式数据库 / 分布式锁服务 Mnesia（内置多副本分布式数据库） 与语言数据结构（Record/Term）零阻抗匹配，无 ORM 转换层
异步削峰与发布订阅 Kafka / RabbitMQ（注：RabbitMQ 本身即 Erlang 编写） 进程邮箱（Mailbox）+ gen_stage / Phoenix.PubSub 百万级邮箱原生内置，无需额外部署和运维独立 MQ 集群
生产环境动态观测 Prometheus + OpenTelemetry + eBPF + 埋点重新发版 observer / recon / BEAM 内置动态 Trace 无需提前打日志、无需重编译，线上直接挂载任意进程追踪入参、返回值与消息流

这并不是说 Kubernetes 或 Redis 没有价值——在多语言异构团队和超大规模集群中，基础设施层的标准化自有其意义。但不可否认的是，绝大多数中大型系统根本没有享受到微服务拆分的收益，反而过早地背上了分布式系统的全部复杂度。

而在 BEAM 的世界里，WhatsApp 曾仅凭寥寥数十名工程师，在单台 BEAM 节点上承载超过 200 万并发长连接；Discord 依靠 Elixir（运行于 BEAM）管理着数百万个同时在线的实时语音与文字 Guild 房间。每一个房间、每一个会话，都只不过是虚拟机里的一个普通进程（GenServer）而已。

4. 2026 的新战场：为什么有状态服务与 AI Agent 又回到了 Actor 模型？

如果说在“切页面 + 查数据库”的传统 CRUD Web 时代，Erlang 的优势还不算显山露水；那么到了 2025–2026 年，随着行业重心剧烈转向 有状态计算（Stateful Computing） 与 AI Agent 编排系统，Erlang 所代表的 Actor 模型迎来了戏剧性的文艺复兴。

4.1 AI Agent 的本质就是 Actor

回想一下 2023 年人们是怎么写大模型应用的：一个无状态的 Python Web 接口收到请求，拼好 Prompt 同步调用一次 LLM API，把返回的文本塞进数据库，请求结束。

但到了 2026 年，真正的生产级 AI 系统早已演变成了长周期、多工具、多智能体协同的状态机网络：

  • 一个主控 Agent 收到复杂任务后，需要并发派生（Spawn）出 5 个子 Agent 分别去检索代码库、运行沙箱测试、查询监控指标；
  • 每个 Agent 都有自己独立的上下文窗口与短期记忆（Private State）；
  • 工具调用随时可能因为外部 API 限流、网络中断、沙箱超时或模型幻觉输出非法格式而失败；
  • 某些敏感操作需要挂起等待人类审批（Human-in-the-loop），几小时甚至几天后再被一条异步事件唤醒继续执行；
  • 当某个子 Agent 陷入死循环或崩溃时，系统不能全盘皆输，而需要父 Agent 捕获退出信号，决定是重试、降级还是换一套 Prompt 重新拉起一个干净的子 Agent。

当你把上面这几条需求连起来读一遍，你会惊讶地发现：这不就是卡尔·休伊特（Carl Hewitt）在 1973 年定义的 Actor 模型，外加 Joe Armstrong 在 1986 年实现的 Erlang 监督树吗？

用无状态的 Python + Celery + Redis 锁去硬凑这套状态机，往往会写出一座由分布式锁、轮询任务和僵尸状态堆成的大山；而在 BEAM 上，一个会话或一个 Agent 就是一个 gen_statem 或 GenServer 进程——内存天然隔离、消息天然排队、超时自带定时器、崩溃自带 Supervisor 兜底。

4.2 Durable Execution 与 Virtual Actor 的遍地开花

不仅在 AI 领域，过去几年后端基础架构领域最热门的两个方向——持久化执行（Durable Execution，如 Temporal、Restate） 与 虚拟 Actor（Virtual Actors，如 Microsoft Orleans、Cloudflare Durable Objects），本质上都是在主流语言生态里重建 Erlang 的核心心智模型：

  1. 计算向状态靠拢（Stateful Serverless）：不再每次请求都从远端数据库拉取全量状态、算完再写回，而是让每个业务实体（订单、物联网设备、文档协作房间、游戏对局）在内存中常驻为一个单线程串行处理消息的 Actor，彻底消灭并发锁竞争；
  2. 用运行时监管替代业务层重试泥潭：把超时、重试、退避、状态快照与崩溃恢复下沉到运行时框架层，让业务代码回归纯粹的顺序逻辑。

4.3 Elixir 与 Gleam：帮 BEAM 补齐最后两块拼图

长期以来，阻碍新一代开发者拥抱 Erlang 的往往不是 BEAM 虚拟机，而是两座表面上的大山：一是 Erlang 继承自 Prolog 的复古语法（句号 .、分号 ;、逗号 , 的区分曾劝退无数新手）；二是动态类型系统在数十万行代码重构时的心智负担。

而站在 2026 年，这两块短板在 BEAM 生态内部都已经有了极佳的答案：

  • Elixir 的工程生态：José Valim 创造的 Elixir 不仅用现代、优雅的语法和强大的元编程宏（Macro）重塑了 BEAM 的开发体验，更通过 Phoenix LiveView（用服务端常驻轻量进程通过 WebSocket 直接驱动差量 DOM 更新，省去前后端分离的繁琐状态同步）和 Nx / FLAME（弹性无服务计算）把 BEAM 带入了现代 Web 与 AI 工程主流；
  • Gleam 与静态类型化：对于追求编译期类型安全的团队，Gleam 在 BEAM 之上提供了一套受 Rust 与 ML 家族启发的健全静态类型系统（Sound Type System）：支持代数数据类型（ADT）、穷尽模式匹配（Exhaustive Pattern Matching）、无 null/无异常的 Result<T, E> 错误处理，编译后直接生成高性能 Erlang 字节码跑在 BEAM 上。与此同时，Erlang 官方自 OTP 27/28 起持续推进的渐进式类型系统也已日趋成熟。

5. 冷静祛魅：Erlang 与 BEAM 不是银弹

当然，回看 Erlang 的伟大，绝不是要把 BEAM 奉为包治百病的神明。恰恰相反，作为一名系统工程师，最应该看清的是：Erlang 的每一项惊人特性，都是用极其明确的工程取舍（Trade-off）换来的。

5.1 纯 CPU 密集型计算与内存布局代价

为了实现“绝对的进程隔离”、“无锁并发”与“软实时抢占”，BEAM 做出了两个底层的妥协：

  1. 不可变数据（Immutability）与装箱表示（Boxed Terms）：在 BEAM 中，一切变量一旦绑定即不可原地修改，复杂数据结构大多通过指针链表或树来共享未修改的部分。这决定了它的缓存局部性（Cache Locality）和内存密度远不如 Rust 或 C++ 的连续结构体数组（Vec<Struct>）；
  2. 算术与字节流吞吐差距：尽管自 Erlang/OTP 24 引入 BeamAsm（原生 JIT 编译器） 以来，Erlang 代码已不再通过字节码解释器执行，而是直接编译为原生 x86_64 / ARM64 机器码，性能提升了 2 到 4 倍；但在紧凑数值循环、矩阵乘法、SIMD 向量化、音视频编解码或超高吞吐零拷贝协议解析上，BEAM 依然比 C / Rust / Go 慢一个数量级。

不过，现代 BEAM 工程实践对此早已形成了一套成熟的混合范式：“用 BEAM 做控制面（Control Plane）与状态编排，用 Rust 做数据面（Data Plane）算子”——通过 Rustler 编写内存安全的 NIF（Native Implemented Functions），并交由 BEAM 的脏调度器（Dirty CPU/IO Schedulers）执行。这样既利用了 Rust 极致的单核 CPU 算力，又不会破坏 BEAM 普通调度器的 4000 Reductions 抢占公平性。

5.2 邮箱积压（Mailbox Bloat）与反压缺失

在 Erlang 中，发送消息 Pid ! Msg 是无界异步非阻塞的——只要目标进程还活着，发送方把消息塞进对方邮箱就立刻返回成功。

这是一把锋利的双刃剑：如果上游生产消息的速度持续高于下游进程的消费速度，下游进程的邮箱队列就会无限增长。当邮箱积压到数十万条消息时：

  1. 内存占用会急剧飙升，最终触发整个节点的 OOM；
  2. 更隐蔽的是，如果代码中使用了选择性接收（Selective Receive）（即模式匹配特定消息），BEAM 每次都需要遍历邮箱里积压的旧消息，导致该进程的 CPU 消耗退化为 $O(N)$，进一步加剧雪崩。

因此，在生产级 Erlang/Elixir 系统中，工程师必须克制滥用裸异步消息（! / cast）的冲动，在关键路径上使用带超时的同步调用（gen_server:call）形成天然反压（Backpressure），或者使用基于需求拉取（Demand-driven）的 gen_stage 流控模型。

5.3 原生分布式集群的规模边界

Erlang 语言内置的分布式集群（Distributed Erlang）采用的是**全互联网格（Full-Mesh）**拓扑，节点之间通过周期性心跳（net_ticktime）维护连接与全局名称注册。

这套机制在 10 到 50 个同机房节点的规模下堪称魔法；但当集群规模扩大到数百个节点，或者跨公网弱连接部署时，全网格心跳的通信开销以及网络分区（Net Split / 脑裂）后的状态合并，依然需要开发者引入像 Partisan 这样的可扩展网络层或基于 CRDT / Raft（如 ra 库）的共识机制来接管。

6. 结语：阿姆斯特朗定律

计算机科学界有一条广为人知的“格林斯潘第十定律”（Greenspun’s Tenth Rule）：

“任何足够复杂的 C 或 Fortran 程序，都包含一个临时拼凑、只有一半功能、漏洞百出且运行缓慢的 Common Lisp 实现。”

站在 2026 年，回望这四十年来后端架构、云原生基础设施与分布式运行时的演进轨迹，我们或许也可以为仙逝的 Joe Armstrong 总结出一条同样深刻的**“阿姆斯特朗定律”（Armstrong’s Law）**：

“任何足够复杂的分布式或高并发后端系统，最终都会在业务代码或基础设施层，临时拼凑出一套只有一半功能、配置繁琐且脆弱不堪的 Erlang/OTP 实现。”

今天，你未必需要把公司里的 Go、Rust 或 Python 服务全部推倒重写成 Erlang。但花一点时间去读一读 BEAM 的调度与内存模型，亲手写一棵 OTP 监督树，去理解四十年前那群电信工程师是如何看待隔离、失败、状态与时间的——当你再次面对满屏的微服务 YAML、分布式锁死锁、协程泄漏和复杂的 Agent 状态机时，你会突然看清哪些是本质问题，哪些只是我们自己制造出来的偶然复杂度。
